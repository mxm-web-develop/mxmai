### 总体目标

- **目标一**：将现有“静态 hard-code 模型 + 路由覆盖”升级为 **DB 驱动的 Provider 模型目录（Catalog）+ 路由管理**，支持 Admin 通过界面为现有 provider 添加/下线物理模型。
- **目标二**：统一 **价格配置、成本核算、平台扣费**，继续使用现有 `provider_pricing` 表，但让它自然地挂在新的模型目录之上。
- **目标三**：升级用量与稳定性统计，做到 **按 provider + model_key + scope + logical_model** 维度统计用量、成本、延迟、成功率与错误分布，并在 Admin 中可视化。
- **目标四**：为每个物理模型提供 **连通性测试与启用流程**，避免配置错误直接进生产流量。

### 一、数据模型与数据库表设计

- **1.1 物理模型目录表 `provider_models`（新增）**
- 作用：承载“不同 provider 下的物理模型列表”，成为所有下拉选择、计费、统计的主数据源。
- 关键字段：
  - `id`：主键
  - `provider`：如 `openai`、`deer`、`replicate`（与 `ProviderType` 一致）
  - `scope`：`writing` / `graph` / `audio` / `video` / `text` / `default`
  - `model_key`：平台内部的物理模型键（建议与上游模型名等价，或可做自定义别名）
  - `upstream_model`：可选，上游真实模型名（当 `model_key` 为别名时使用）
  - `display_name`：Admin 界面展示名
  - `description`：简要说明
  - `capabilities`：JSON（如是否支持多模态、最大上下文长度、是否支持工具调用、图片分辨率等）
  - `default_parameters`：JSON（模型级默认参数，如 temperature、max_tokens 等）
  - `is_enabled`：布尔，决定是否出现在下拉和被路由到
  - `created_at` / `updated_at`
- **1.2 保持 `provider_pricing` 为“价格表”，与 `provider_models` 通过 `provider + model_key + scope` 关联**
- 不改动现有 `provider_pricing` 结构，继续作为：
  - Provider 成本（USD）：`unit_price` / `input_unit_price` / `output_unit_price` + `currency`
  - 平台售价（MXM-TOKEN）：`platform_*` 字段
  - 计费模式：`charge_mode`（`token_based` / `per_image` / `per_second_*` / `per_request`）
- 约定：
  - `provider_pricing.provider` + `provider_pricing.model_key` + `provider_pricing.scope` 必须对应一条 `provider_models` 记录（可通过 Admin 校验和前端联动保证）。
- **1.3 业务路由覆盖表 `model_routing_overrides`（沿用）**
- 现有 schema 已可用（`logical_model`, `provider`, `model`）。
- 约定：`model` 字段统一存储为对应 `provider_models.model_key`，避免混用上游原始名。
- 在写入和读取时，如果 `provider_models.is_enabled=false`，则视为无效配置，可：
  - 后端返回错误提示给 Admin；
  - 或在运行时 fallback 到默认路由。
- **1.4 统计表扩展**
- `provider_usage_records`：保留现有结构，继续作为“成功调用的用量/成本事实表”。
- `provider_call_stats`：增加字段用于精细统计：
  - 新增 `model_key`、`scope`、`task_id` 字段（以及可选 `logical_model` 若尚未存）。
  - 确保所有调用都写入（成功/失败），用于计算延迟与成功率。

### 二、服务层与 Provider 层改造

- **2.1 模型注册/查找从硬编码转为“静态默认 + DB 动态”**
- 现状：`[mxmcgi/src/models/registry.ts](mxmcgi/src/models/registry.ts)` 中的 `registerModel()` 只收集编译期静态定义的模型；`ProviderFactory` 通过它构建 `modelProviderMap`。
- 目标：在不破坏现有静态模型的前提下，增加 DB 动态模型：
  - 启动时或首次访问时，从 `provider_models where is_enabled=true` 读取记录。
  - 将这些记录转换为简化版 `ModelDefinition` 注入 registry，或者在 `ProviderFactory.buildModelProviderMap` 内部直接合并 DB 结果。
  - 确保 `ProviderFactory.getProviderForModel()` 能识别新加入的 `model_key`。
- **2.2 各 provider 的 `supportsModel` / 上游解析走 DB 模型目录（已落地）**
- 实现要点：`[mxmcgi/src/models/provider-model-catalog.ts](mxmcgi/src/models/provider-model-catalog.ts)` + `[mxmcgi/src/models/physical-model-id.ts](mxmcgi/src/models/physical-model-id.ts)`；各 Provider 已改为以 `provider_models` 为准，**静态 `suport-list` 已删除**。
- **2.3 ProviderFactory 与路由解析保持兼容并增强维度**
- 保持 `[mxmcgi/src/core/providers/index.ts](mxmcgi/src/core/providers/index.ts)` 现有逻辑：
  - `getProviderAndModel(logicalOrPhysicalName, preferredProvider?)` 先走 `getResolvedRouting()`，再 fallback 到 `getProviderForModel()`。
- 增强点：
  - 当从路由中拿到 `provider + model` 时，确保 `model` 是 `provider_models.model_key`。
  - 在构建 `modelProviderMap` 时，合入 `provider_models` 的启用模型，让 `getProviderForModel()` 还能处理“只在 DB 里存在的新模型”。

### 三、Admin 接口与前端改造

- **3.1 Provider 模型目录管理接口（后端）**
- 在 `[mxmcgi/src/routes/providers.ts](mxmcgi/src/routes/providers.ts)` 新增一组 Admin 路由：
  - `GET /system/admin/providers/models`：分页/过滤查询 `provider_models`。
  - `POST /system/admin/providers/models`：创建新物理模型（指定 provider/scope/model_key/upstream_model/capabilities/default_parameters）。
  - `PUT /system/admin/providers/models/:id`：编辑模型信息与 `is_enabled`。
  - `DELETE /system/admin/providers/models/:id`：逻辑删除或严格禁止删除（仅允许 `is_enabled=false`）。
  - 与现有 `/options` 接口联动：
    - 现有 `getProvidersOptions` 已返回 `modelsByProvider`、`modelsByProviderByScope`。
    - 改造为：优先基于 `provider_models where is_enabled=true` 构建；不足部分再合并 registry 中的静态模型。
- **3.2 前端 Admin 页面扩展（`ProviderRoutes` + 新页面）**
- 基于 `[web/src/pages/ProviderRoutes.tsx](web/src/pages/ProviderRoutes.tsx)` 现有 Tabs 结构：
  - 新增“**物理模型目录**” Tab：
    - 表格列：provider / scope / model_key / upstream_model / 简要说明 / 是否启用 / 最近测试状态 / 操作。
    - 操作包括：新增/编辑/禁用/连通性测试/查看关联定价。
  - 在“模型价格管理” Tab 中：
    - 使用 `/providers/options` 返回的模型列表填充 `model_key` 下拉（已存在逻辑基础，改为从新 options 数据源来）。
- **3.3 价格与余额视图保持现有 UI，只补充交互细节**
- `provider_pricing` 表已经在前端展示：
  - 增加一个列或 tooltip 显示该价格行是否有对应 `provider_models` 记录；没有时在 UI 给出提示（可点击“一键创建模型”）。
- 余额卡片视图保持不变，只在需要时展示更多诸如“该 provider 下启用模型数量”的统计信息（非必需）。
- **3.4 连通性测试接口与前端交互**
- 后端在 `providers` 路由中新增：
  - `POST /system/admin/providers/models/test`：
    - 入参：`provider_model_id` 或 (`provider`, `model_key`, `scope`)，以及可选 `testPayload`。
    - 逻辑：
      - 根据 scope 选用最小成本、最轻量的测试 prompt/参数（例如文本用一个固定简短 prompt，max_tokens=8；图片选择最小尺寸等）。
      - 使用对应 provider 的 `generate()` 调用；
      - 捕获 latency、错误信息，写入 `provider_model_tests` 表，并返回测试结果。
  - 可选：`GET /system/admin/providers/models/:id/tests` 查看最近 N 次测试记录。
- 前端：
  - 在“物理模型目录”表格中为每行提供“测试连通性”按钮，弹出结果弹窗并在行内显示最近测试状态（成功/失败 + 时间 + latency）。
  - 可选择约束：只有最近一次测试成功后才能把 `is_enabled` 切为 true（在前端和后端均做校验）。

### 四、统计与报表升级

- **4.1 请求级统计埋点调整**
- 在统一调用入口（例如 `runByModelKeyAnyScope` 或 `TaskExecutor.callModelGenerate` 所在文件，如 `[mxmcgi/src/task/task-executor.ts](mxmcgi/src/task/task-executor.ts)`）做一次完整埋点：
  - 在解析出 `provider + model_key + scope + logical_model` 后记录 `start = Date.now()`。
  - 调用 `provider.generate()`。
  - 在 `try/finally` 中调用 `recordStats`，并传入：
    - `provider`
    - `logicalModel`（逻辑模型名）
    - `latencyMs`
    - `success`
    - `errorCode`（HTTP 状态码/上游 error_type/内部错误标识）
    - 同时，在 `recordStats` 内将 `model_key`、`scope`、`task_id` 一并写入 `provider_call_stats` 表。
- **4.2 聚合接口按 provider+model 维度输出**
- 在 `[mxmcgi/src/core/providers/provider-stats.ts](mxmcgi/src/core/providers/provider-stats.ts)`：
  - 扩展 `ProviderStatsAggregate`，增加可选字段 `modelKey?` 和 `logicalModel?`。
  - 在 `getProviderStats()` 中增加 `groupBy` 参数（`provider` / `provider_model` / `logical_model`）：
    - 当 `groupBy='provider_model'` 时，按 `provider + model_key` 聚合并返回指标（请求数/成功数/错误率/avg/p50/p95 等）。
  - 保持当前按 provider 聚合的行为作为默认值，前端现有视图无需修改。
- **4.3 成本统计与用量报表复用现有 `provider_usage_records`**
- 已有的成本估算逻辑（在 `providers/costs` 接口和相关 service 中）可保持：
  - 只需保证使用 `provider_usage_records` 的 SQL 与新的 `provider_models` 一致（按 `provider + model_key + scope` 聚合）。
  - 在 Admin 中增加一个“按模型”视图（类似你们现在 `groupBy=model` 的成本报表），结合上一步的性能统计，形成“**某模型的成本/收益/性能综合视图**”。

### 五、与计费/余额体系的集成

- **5.1 Provider 成本扣减流程保持不变**
- `[mxmcgi/src/statistics/usage-service.ts](mxmcgi/src/statistics/usage-service.ts)` 已经：
  - 把 usage 写入 `provider_usage_records`；
  - 调用 `ProviderBalanceService.deductFromUsage()` 基于 `provider_pricing` 从 `provider_balances` 扣减成本。
- 在新方案中，只需保证：
  - 所有成功调用的 `result.metadata.provider` 与 `result.metadata.model` 均为 `provider` 和 `model_key`；
  - scope 推断函数 `inferScope()` 对新增的逻辑模型命名保持兼容。
- **5.2 用户侧扣费（MXM-TOKEN）保持不变，仅依赖更准确的 provider/model/scope**
- `[mxmcgi/src/core/billing/billing-service.ts](mxmcgi/src/core/billing/billing-service.ts)` 已通过 `getPricing(provider, modelKey, scope)` 读取 `provider_pricing` 并计算平台扣费。
- 在路由和模型目录升级后：
  - 保证任务 metadata 中写入的 provider/model/scope 一致且来源于 `provider_models`；
  - 这样无论是成本端还是用户扣费端，都会以同一套键值为原子。

### 七、后续可选增强

- **7.1 模型权重与灰度路由**
- 为 `model_routing_overrides` 增加可选字段（或新表）保存多个候选物理模型及权重：
  - 例如：`writing-outlines` → `[{provider: deer, model: gemini-3-pro, weight: 0.7}, {provider: openai, model: gpt-5-nano, weight: 0.3}]`。
  - 在 `getResolvedRouting` 或上层逻辑中随机/分流，实现灰度发布和 AB test。
- **7.2 参数模板 & Schema 驱动表单**
- 在 `provider_models` 的 `capabilities` 中存储简化的参数 schema：
  - 例如 token 范围、支持的 sampling 参数等。
  - Admin 将来可以基于这些 schema 自动生成“模型测试表单”，减少硬编码表单字段。
- **7.3 多租户 / 子 service 统计与限流**
- 在 `provider_call_stats` 与 `provider_usage_records` 中引入 `service` / `tenant_id` 维度：
  - 用于区分不同业务线/租户对同一模型的消耗和稳定性表现；
  - 未来可以在 Provider 层做“按 tenant 限流或熔断”。
